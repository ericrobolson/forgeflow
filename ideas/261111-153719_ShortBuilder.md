# Short builder

Status: idea only. Not scheduled.

`"raw/painting-0311.mp4" short-paths make-short` takes a long recording (a painting session, a Twitch VOD, a music production session, gameplay), finds the good part, cuts it into a vertical Short that follows a fixed structure, and opens a native window where the draft is already done. Editing means nudging, not building: drag a handle, swap a pick, fix a caption, press Enter. The result is rendered to a known output folder, with an edit file beside it so it can be re-rendered or re-opened later.

## Background

Two references prompted this:

- dev.to, "I built a free AI pipeline for YouTube Shorts using FFmpeg" (numbpill3d). It describes the workflow only at a high level: describe the edit, have an LLM write the ffmpeg command, run it. It contains no clip selection, reframing method or commands.
- github.com/numbpill3d/ffmpeg-ai (Python, MIT). It goes from a topic to a "faceless" narrated video: an OpenRouter script, edge-tts voiceover, AI images with Ken Burns pans and xfade, faster-whisper ASS karaoke captions, music with sidechain ducking, and an H.264/AAC encode at 1080×1920 or 1920×1080.

ffmpeg-ai solves a different problem. It generates content from nothing; we have hours of footage and need to find 30–60 good seconds and reformat them. The parts worth borrowing are ideas, not code:

- **Captions:** word-level whisper timestamps written as ASS karaoke (`\k` tags), in a few named styles (karaoke, plain, bold-center).
- **Output specs** as constants per mode (resolution, fps, codec arguments).
- **Music ducking** with ffmpeg `sidechaincompress`.
- **A cache per job** plus a `run_report.json`, so single stages can re-run.

## Concepts

### Folder arguments and category selection

```
shorts/
  inbox/
    twitch/        ← drop sources here (or pass a path to make-short)
    painting/
    music-prod/
    gameplay/
  categories/      ← one JSON per category: how to fill the program's slots
  programs/        ← the structure Shorts follow
  profiles/        ← per-setup screen regions (facecam, canvas, DAW, game)
  work/<sha>/      ← signal cache, proxy, draft edit
  out/
    review/        ← rendered, waiting
    approved/      ← moved here = ready to post
    rejected/
```

Every folder is an explicit argument, supplied in a `paths` map to the words that need it. There is no implicit `shorts/` root, current-directory lookup, global folder config, or fixed home-directory location. The tree above is one possible arrangement; each folder can live elsewhere. Required keys are `inbox_dir`, `categories_dir`, `programs_dir`, `profiles_dir`, `work_dir`, `assets_dir`, `review_dir`, `approved_dir`, and `rejected_dir`. Batch runs read `inbox_dir`; review operations receive the review, approved, and rejected destinations from this same map. Single-source operations use the explicit source path. Validate the needed arguments before starting work; report missing folders clearly and create writable work/output folders as needed.

Paths inside category/program files, such as `music/lofi/` and `end_card.mov`, resolve against the supplied `assets_dir`. Category, program, and profile names resolve only inside their corresponding supplied directories. Source and folder arguments are normalized to absolute paths at entry. Save the resolved paths in the edit JSON so reopening and rendering do not depend on the working directory.

The category comes from the source's parent folder name, or from a sidecar `<source>.json` (`{"category": "painting", "profile": "desk-overhead"}`), or from an explicit argument. Review can be just moving files between folders; rejected drafts keep their scores, which can be used later to tune the weights.

### Program: the fixed structure every Short follows

A program is an ordered list of named slots with length bounds. Every Short in a category has the same rhythm, end card and caption style, which keeps the channel consistent and makes selection a narrow question per slot instead of "find something good".

```json
// programs/standard.json
{
  "slots": [
    { "name": "hook",   "len": [1.5, 3] },
    { "name": "setup",  "len": [3, 8] },
    { "name": "build",  "len": [10, 30], "flex": true },
    { "name": "payoff", "len": [3, 10] },
    { "name": "outro",  "len": [1, 2], "card": true }
  ],
  "max_len": 50,
  "captions": "on_speech",
  "end_card": "end_card.mov"
}
```

`flex` slots stretch or shrink to hit the length. To A/B test, add another program (for example `cold-open`: payoff, then rewind to the setup), render the same source with both, and compare retention.

### Category: how each slot gets filled

| Slot | Twitch | Painting | Music prod | Gameplay |
|---|---|---|---|---|
| hook | the peak, clipped early | the finished piece, 1.5 s | the drop | the kill / clutch frame |
| setup | ~5 s before the peak, snapped to the transcript | blank canvas | first sound / empty project | the moment before the engagement |
| build | lead-up to the peak | compressed timelapse | layers being added, cut on beats | the fight at real speed |
| payoff | the peak, full | slow reveal / zoom out | the full loop playing | the kill and the reaction |
| outro | end card | end card + title | end card | end card |

```json
// categories/painting.json
{
  "program": "standard",
  "profile": "desk-overhead",
  "layout": "canvas_crop",
  "slots": {
    "hook":   { "pick": "last_frame_hold" },
    "setup":  { "pick": "first_stable_frame" },
    "build":  { "pick": "progress_compress", "speed": "auto" },
    "payoff": { "pick": "last_frame_zoomout" }
  },
  "audio": { "music": "music/lofi/", "duck": "voice" },
  "captions": "speech_only",
  "max_per_source": 1
}
```

A long source can produce several Shorts: each candidate payoff is an anchor, a program is built around each one, overlapping anchors are skipped, and the count is capped by `max_per_source`.

### Signals (computed once, cached by source hash)

| Signal | How | Used by |
|---|---|---|
| Loudness, spikes | ffmpeg `ebur128` | twitch, gameplay |
| Silence | `silencedetect` | snapping cuts, twitch, painting voiceover |
| Scene changes | `scdet` | gameplay, music |
| Visual progress (frame difference, hand masked) | downsampled frames | painting |
| Transcript, word-level timing | whisper.cpp | twitch, captions everywhere |
| Chat density, emote spikes | TwitchDownloaderCLI chat JSON | twitch (the strongest signal there) |
| Beats, onsets, sections | aubio or a small onset detector | music, gameplay montages, beat-snapped cuts |
| Where on screen the motion is | motion map on a proxy | music (DAW zoom), gameplay crop |
| Vision tags on sampled frames | contact sheet → vision model | all, optional and last (slowest) |

Pickers (`last_frame_hold`, `progress_compress`, `peak_window`, `drop`, `beat_montage`, ...) read signals and return time ranges. A new category is one JSON file; code changes only when a new picker is needed.

### Layouts: autoformat to portrait

Each layout turns a landscape source into 1080×1920 using regions from the profile:

- **`stack`**: facecam region on top (~1/3 of the height), gameplay or screen region below. For Twitch.
- **`canvas_crop`**: crop to the canvas region, scaled to fill, with a blurred fill where the aspect ratio doesn't match. For painting.
- **`motion_zoom`**: a crop that follows the motion map, smoothed so it doesn't jitter, over a blurred full-frame copy or a `showspectrum`/`showwaves` strip. For music production (DAW screens are unreadable when scaled down whole).
- **`center` / `follow`**: a center crop, or a motion-weighted crop that follows the action. For gameplay.
- **`letterbox_blur`**: the full frame letterboxed over a blurred zoom of itself. The fallback for strategy games or UI-heavy screens.

### Audio policy per category

- **twitch:** keep the voice; `loudnorm` to -14 LUFS.
- **painting:** music with sidechain ducking under the voice when there is any.
- **music-prod:** never duck or add music. Use bounced stems or the master when available (much cleaner than the screen-capture audio, and beat or drop detection becomes nearly exact); `loudnorm` only.
- **gameplay:** keep the game audio; if music is added, duck it under the game's sound effects.

## In ForgeFlow

ForgeFlow already has the pieces this needs:

- a native window process (`forgeflow __pick`, `src/picker.rs`, eframe) with a frame slider, used by `pick-box` / `pick-points`
- ffmpeg frame extraction (`video_frame`, `video_duration`)
- `finish-video` for upscaling and frame interpolation
- `toolchain.rs` for building pinned native tools (llama-server, sd-cli); whisper.cpp would be built the same way
- `ops::pause_for` for GPU sharing
- a chat model for judgment calls

### Words

Small, composable words, with `make-short` as the one-liner over them:

```forth
\ short-paths is a caller-defined word that pushes the explicit paths map:
\ { inbox_dir, categories_dir, programs_dir, profiles_dir, work_dir,
\   assets_dir, review_dir, approved_dir, rejected_dir }
\ Example values can follow the shorts/ tree above; none are built-in defaults.

\ one-time setup per camera/OBS scene: drag boxes for facecam, game, canvas, DAW...
"desk-overhead" "raw/sample.mp4" short-paths define-regions
                           ( profile path paths -- profile-path )

\ the steps make-short runs, usable on their own
"raw/vod.mp4" short-paths analyze-video
                           ( path paths -- work-dir )        \ signals + proxy, cached
"raw/vod.mp4" "twitch" short-paths draft-short
                           ( path category paths -- edit )   \ program filled, edit JSON path
"work/…/edit-1.json" edit-short
                           ( edit -- edit )                  \ saved paths; Esc cancels
"work/…/edit-1.json" short-paths render-short
                           ( edit paths -- out-path )        \ explicit output destination

\ all of it
"inbox/painting/0311.mp4" short-paths make-short
                           ( path paths -- out-path )
```

`make-short` = `analyze-video` → `draft-short` → `edit-short` → `render-short`. It passes the supplied folder arguments through each stage and writes to `<review_dir>/<category>/<source-stem>-<n>.mp4` with the edit JSON beside it. A `--no-edit` variant (or `make-short-auto`) skips the window for batch runs over an inbox; `edit-short` on the saved JSON re-opens any draft later.

`define-regions` extends the `pick-box` window: several named boxes on one frame instead of one box, saved to a profile. Regions are set once per camera position or OBS scene layout, not per video.

Everything the window changes is data, so a render is reproducible and re-editable:

    "programs_dir": "/media/shorts/programs",
    "profiles_dir": "/media/shorts/profiles",
    "work_dir": "/media/shorts/work",
    "assets_dir": "/media/shorts/assets",
    "review_dir": "/media/shorts/out/review",
    "approved_dir": "/media/shorts/out/approved",

### The editor window (`edit-short`)

The draft is already complete when it opens, so editing is a quick pass:

```
┌ edit-short: 2026-11-10.mp4 · twitch · standard ────────────────────────┐
│ ┌─ source (landscape) ──────────────┐   ┌─ output 9:16 ─┐              │
│ │  [facecam box]                    │   │  facecam      │  title       │
│ │                                   │   │───────────────│  [........]  │
│ │       [main box]                  │   │  gameplay     │  hook text   │
│ │                                   │   │  "wait WAIT"  │  [........]  │
│ └───────────────────────────────────┘   └───────────────┘              │
│ ▕hook▕setup ─────▕build ──▕payoff ────────▕outro▏   0:31 / 0:50        │
│  source timeline: ▁▂▁▅█▃▁ (loudness)  ▁▁▃▇▂ (chat)  ◆ alternates      │
│ captions: 5402.4 wait wait WAIT  ✎                                     │
│ [Space] play  [ / ] nudge in/out  [Tab] next slot  [A] next alternate  │
│ [L] cycle layout  [R] re-pick slot  [Enter] render  [Esc] cancel       │
└────────────────────────────────────────────────────────────────────────┘
```

- **Both views:** the source frame with the region boxes (draggable) and a live 9:16 output preview with safe-area guides (where YouTube's UI covers the bottom and right).
- **Slot strip:** one block per program slot. Drag the edges to trim; the flex slot absorbs the change so the total stays within `max_len`.
- **Signal lanes** under the source timeline (loudness, chat, beats, progress), so you can see why a moment was picked and grab a better one.
- **Alternates:** the next-best anchors, one key away. Pressing `A` rebuilds the draft around the next one.
- **Captions:** a list of lines; click to edit text. Timing comes from whisper and is not edited by hand.
- **Crop keyframes** for `follow` / `motion_zoom`: the auto path is shown and can be overridden at a frame.
- Enter renders the final file and closes the window; the program continues with the output path. Esc cancels and leaves the draft JSON in place.

The window runs as its own process (`forgeflow __edit-short <spec>`), like the picker. Previews read from a low-res proxy (for example 540p, all-intra or with short GOPs) made by `analyze-video`, so scrubbing is fast.

### Preview audio: rodio

Use `rodio` for audio playback inside the editor process. Keep its output stream alive for the window's lifetime and isolate device access and playback state from the edit/timeline logic. ffmpeg decodes source audio and builds a cached PCM preview under the supplied `work_dir`; rodio sends that preview to the audio device. There is no separate ffplay window or process.

The preview follows the edited output timeline: slot order, trims, speed changes, music, ducking, normalization, and end-card audio use the same edit data and ffmpeg audio-filter construction as the final render. Rebuild affected preview audio when those edits change, discarding stale work. Use a bounded buffer or disk-backed PCM cache rather than loading a long source recording into memory.

Space starts or pauses audio and video together. Drive video presentation from the audio playback position during playback to prevent drift. Seeking stops and clears queued audio, positions the preview at the new output timestamp, and resumes only if playback was active; scrubbing while paused stays silent. Slot jumps, alternate selection, and speed changes reset both views and audio to the same output position. Sources with no audio use the timeline clock. If the output device fails, show a clear error and allow silent preview; rendering remains available.

### Rendering

`render-short` builds one ffmpeg filtergraph from the edit JSON using fixed templates per layout. The LLM never writes ffmpeg commands, so renders are deterministic and testable (golden filtergraph strings in tests). Steps: trim and concat the slots → apply the layout (crop/scale/stack/blur) → burn ASS captions → mix audio (duck, `loudnorm`) → append the end card → H.264/AAC 1080×1920, 30 or 60 fps. `finish-video` is available when a source needs upscaling.

### Where the model is used

Only for judgment, never for structure:

- confirming and ranking candidate payoffs from transcript excerpts and signal summaries
- writing the hook text and the title
- picking stage frames from a contact sheet (painting) or tagging events (gameplay), with a vision model when one is available

With no chat model configured, it falls back to signal scores only and uses no titles.

## Build order

1. Edit JSON schema, `render-short` with the `stack` and `canvas_crop` layouts, and captions. Testable with hand-written edit files.
2. `define-regions` (multi-box picker) and profiles.
3. `analyze-video`: proxy, loudness, silence, scene changes, whisper.cpp via `toolchain.rs`.
4. `draft-short` with the `standard` program and the twitch category (chat-spike + loudness `peak_window`).
5. `edit-short` window: slot strip, previews, nudging, alternates, and rodio audio playback synchronized with video. Verify pause/resume, seeks, slot transitions, speed changes, and silent sources.
6. Painting (`progress_compress`, `canvas_crop`).
7. Beats and onsets; music-prod (`drop`, `motion_zoom`, stems) and gameplay (`beat_montage`, `follow`).
8. Vision tagging; `make-short-auto` over an inbox; the move-to-approved/rejected feedback loop.

## Open questions

- **Painting capture setup:** overhead camera, tablet screen capture (OBS), or both? Is there talking while painting? This decides `canvas_crop` against a picture-in-picture of both.
- **Twitch sources:** own raw OBS recordings (facecam possibly on a separate track or a separate file) or downloaded VODs plus chat? With separate tracks, `stack` needs no regions at all.
- **Music production:** OBS screen plus system audio, and can stems or the master be exported per session? With clean audio, beat snapping and drop detection become nearly exact.
- **Posting:** the YouTube Data API upload from the supplied `approved_dir`, or keep posting by hand?
- **One program for everything, or per category:** proposed is one shared `standard` that categories may override.
